## 1. Scope

### 1.1 Applicability

This specification applies to EVERY repository within the Lingmo Desktop project that contains C++ header files, including:

- Repositories that produce shared libraries with a public API
- Repositories that produce plugins loaded at runtime
- Repositories that produce executables with internal header dependencies
- Header-only utility repositories

### 1.2 Exceptions

The following repository types are EXEMPT from specific sections as noted:

- **Data-only repositories** (`lingmo-assets`): Exempt from all sections.
- **QML-only repositories** (no C++): Exempt from Sections 5, 6, 7. Section 2 applies only to C++ headers that accompany QML plugins.
- **Specification repository** (`lingmo-specs`): Exempt from all sections.

### 1.3 Supersession Notice

Sections 4 (Public Headers), 5.1 (Private Headers), and 5.2 (Internal Headers) of SPEC-REPO-001 are superseded by this document. All repositories MUST migrate to the rules defined herein within one major release cycle.

## 2. Public Header Layout

### 2.1 Location

[REQ-HDR-001] Every repository that exposes a public C++ API MUST place its public headers in a top-level `include/` directory.

[REQ-HDR-002] The `src/` directory MUST NOT contain public headers. The `include/` directory is the exclusive location for headers that are installed.

> *Rationale*: A single public header root enables predictable include paths, simplifies packaging, and prevents accidental installation of internal headers.

### 2.2 Directory Hierarchy

[REQ-HDR-003] Within `include/`, the directory structure MUST mirror the CMake target name. Each library target SHALL have its own subdirectory named after the target:

```
include/
└── <TargetName>/
    ├── <TargetName>.h
    ├── <TargetName>Export.h
    └── ...
```

[REQ-HDR-004] The `<TargetName>` MUST match the CMake target name as defined in SPEC-REPO-001 Section 6.3.

Examples:

| CMake Target | Include Directory | Path Prefix |
|---|---|---|
| `LingmoTheme` | `include/LingmoTheme/` | `<LingmoTheme/` |
| `LingmoConfig` | `include/LingmoConfig/` | `<LingmoConfig/` |
| `LingmoShellCore` | `include/LingmoShellCore/` | `<LingmoShellCore/` |

[REQ-HDR-005] A repository that produces multiple library targets MUST maintain a separate subdirectory under `include/` for each target. Shared utility headers used by multiple targets within the same repository MUST be placed under `include/Lingmo<RepoName>Common/`.

### 2.3 Module Root Header

[REQ-HDR-006] Each public header directory MUST contain a module root header named `<TargetName>.h`. This header SHALL include every public header in the module, providing a single include point for consumers.

> *Rationale*: A root header simplifies migration when internal structure changes. Consumers that include the root header are insulated from file renames and reorganizations.

[REQ-HDR-007] The module root header MUST NOT contain any declarations. It SHALL consist exclusively of `#include` directives and doxygen module documentation.

[REQ-HDR-008] The module root header MUST use the following structure:

```cpp
#pragma once
#include <TargetName/Export.h>
#include <TargetName/SubComponentA.h>
#include <TargetName/SubComponentB.h>
```

### 2.4 Version Header

[REQ-HDR-009] Every library target MUST provide a version header named `<TargetName>Version.h` installed to the same directory as other public headers.

[REQ-HDR-010] The version header MUST define the following preprocessor macros:

| Macro | Value | Example |
|---|---|---|
| `<TARGET>_VERSION_MAJOR` | Major version integer | `1` |
| `<TARGET>_VERSION_MINOR` | Minor version integer | `0` |
| `<TARGET>_VERSION_PATCH` | Patch version integer | `0` |
| `<TARGET>_VERSION_STR` | Stringified version | `"1.0.0"` |

Where `<TARGET>` is the uppercased CMake target name: `LINGMOTHEME_VERSION_MAJOR`, `LINGMOTHEME_VERSION_STR`, etc.

[REQ-HDR-011] The version header MUST be auto-generated by the build system from the CMake `project(VERSION ...)` value. It MUST NOT be hand-maintained.

### 2.5 Subdirectory Nesting

[REQ-HDR-012] Public headers SHOULD use a flat directory structure. Nesting beyond one level (e.g., `include/LingmoTheme/Detail/Foo.h`) MUST be justified by a documented API surface area exceeding 20 public headers in the subdirectory.

[REQ-HDR-013] When nested subdirectories are used, each nested directory MUST contain a module root header named after the directory. For example, `include/LingmoTheme/Detail/Detail.h`.

### 2.6 Header Content Rules

[REQ-HDR-014] Every public header MUST begin with `#pragma once` as its first substantive line (SPEC-REPO-001 §4.4).

[REQ-HDR-015] Every public header MUST include the corresponding `<TargetName>Export.h` immediately after `#pragma once`.

[REQ-HDR-016] Every public header MUST include only the headers it directly uses. Transitive includes MUST NOT be relied upon. Consumers MUST be able to include any public header without first including another header.

[REQ-HDR-017] Public headers MUST NOT include any private header (`*_p.h`) or internal header (`detail/*`).

[REQ-HDR-018] Forward declarations SHOULD be used instead of includes where the included type appears only as a pointer, reference, or function parameter.

## 3. Private Headers

### 3.1 Definition

[REQ-HDR-019] A private header is a header that contains declarations used across multiple translation units within a single library but NOT exposed to consumers of the library.

### 3.2 Location

[REQ-HDR-020] Private headers MUST reside in a `private/` subdirectory directly under the `src/` tree:

```
src/
├── <TargetName>/
│   ├── private/
│   │   ├── <TargetName>_p.h
│   │   ├── Backend_p.h
│   │   └── PlatformHelpers_p.h
│   ├── <TargetName>.cpp
│   └── <TargetName>_p.cpp
```

[REQ-HDR-021] The `private/` directory MUST be at the same level as the implementation files it serves, not at the `src/` root.

### 3.3 Naming

[REQ-HDR-022] Every private header MUST use the `_p.h` suffix as defined in SPEC-CORE-001 (§6.3). The base name SHOULD match the class or module it supports.

Examples:
- `LingmoTheme_p.h` — private declarations for `LingmoTheme`
- `Backend_p.h` — private declarations for `Backend`

### 3.4 Restrictions

[REQ-HDR-023] Private headers MUST NOT be installed. The CMake `install()` directive for private headers is FORBIDDEN.

[REQ-HDR-024] Private headers MUST NOT be included from any public header.

[REQ-HDR-025] Private headers MAY be included from other private headers within the same library target.

### 3.5 Internal Headers

[REQ-HDR-026] An internal header is a header whose declarations are scoped to a single translation unit or a tightly coupled set of implementation files. Internal headers MUST NOT be used across distinct library targets.

[REQ-HDR-027] Internal headers MUST be placed in a `detail/` subdirectory beneath the source:

```
src/<TargetName>/detail/hash_helpers.h
src/<TargetName>/detail/platform_detect.h
```

[REQ-HDR-028] Internal headers MUST NOT use the `_p.h` suffix. They MUST use conventional `.h` extension.

[REQ-HDR-029] Internal headers MUST NOT be installed. They MUST NOT be included by any file outside the owning repository.

## 4. Include Paths

### 4.1 Canonical Include Syntax

[REQ-HDR-030] All includes of Lingmo headers MUST use the angle-bracket form with the target-subdirectory prefix:

```cpp
#include <LingmoTheme/Theme.h>
#include <LingmoTheme/Theme_p.h>       // private — only in .cpp or other private headers
```

[REQ-HDR-031] The path after the angle brackets MUST match the physical directory structure under `include/` for public headers and under `src/` for private headers, relative to the CMake target's include directory.

### 4.2 Quoted Includes

[REQ-HDR-032] Quoted includes (`#include "..."`) MUST be used ONLY for:

1. Including the corresponding header in a `.cpp` implementation file
2. Including headers from the same private/internal scope that are not part of any installed include directory

[REQ-HDR-033] The corresponding header include in a `.cpp` file MUST use the quoted form without directory prefix:

```cpp
// src/LingmoTheme/Theme.cpp
#include "Theme.h"                      // corresponding header
#include "private/Theme_p.h"            // same-directory private header
#include <LingmoConfig/Config.h>        // different target — angle bracket
```

### 4.3 Forbidden Patterns

[REQ-HDR-034] The following include patterns are FORBIDDEN:

| Pattern | Example | Reason |
|---|---|---|
| Relative parent traversal | `#include "../Foo.h"` | Breaks when headers are moved; non-portable |
| Absolute filesystem paths | `#include "/usr/include/..."` | Non-portable; assumes installation path |
| No prefix, angle bracket | `#include <Theme.h>` | Ambiguous; pollutes global namespace |
| File extension omission | `#include <LingmoTheme/Theme>` | Non-standard; confuses tooling |
| Glob includes | `#include <LingmoTheme/*.h>` | Not valid C++ |

[REQ-HDR-035] CMake target include directories MUST be configured such that:

- The `include/` directory is added as a `PUBLIC` or `INTERFACE` include directory
- The `src/` directory is added as a `PRIVATE` include directory
- No broader parent directory is added (e.g., adding `include/../` is FORBIDDEN)

### 4.4 Include Path Configuration

[REQ-HDR-036] For a library target `LingmoTheme`, the CMake include configuration MUST be:

```cmake
target_include_directories(LingmoTheme
    PUBLIC
        "$<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>"
        "$<INSTALL_INTERFACE:${CMAKE_INSTALL_INCLUDEDIR}>"
    PRIVATE
        "$<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/src>"
)
```

## 5. Export Macros

### 5.1 Naming

[REQ-HDR-037] Export macros MUST follow the pattern `LINGMO<MODULE>_EXPORT` as defined in SPEC-CORE-001 (§8.1) and SPEC-REPO-001 (§4.6). `<MODULE>` is the uppercased CMake target name with the `Lingmo` prefix removed.

### 5.2 Export Header

[REQ-HDR-038] The export macro MUST be defined in a header file named `<TargetName>Export.h` located in the target's public include directory:

```
include/LingmoTheme/LingmoThemeExport.h
```

[REQ-HDR-039] The export header MUST be auto-generated by CMake using `generate_export_header` or equivalent. It MUST NOT be hand-written.

[REQ-HDR-040] The export header MUST define the correct visibility for each platform:

| Platform | Shared Library | Static Library |
|---|---|---|
| Linux (GCC/Clang) | `__attribute__((visibility("default")))` | empty |
| Windows (MSVC) | `__declspec(dllexport/dllimport)` | empty |
| macOS (Clang) | `__attribute__((visibility("default")))` | empty |

### 5.3 Application

[REQ-HDR-041] Every declaration that is part of the public ABI MUST be annotated with the export macro:

```cpp
class LINGMOTHEME_EXPORT Theme { ... };
LINGMOTHEME_EXPORT Theme* themeInstance();
```

[REQ-HDR-042] Declarations that are NOT part of the public ABI MUST NOT be annotated with the export macro. They MUST be placed in an anonymous namespace, a `detail` namespace, or annotated with `Q_DECL_HIDDEN`.

### 5.4 Deprecation

[REQ-HDR-043] Deprecated public declarations MUST be annotated with the export macro AND the `[[deprecated]]` attribute:

```cpp
LINGMOTHEME_EXPORT [[deprecated("Use Theme::instance() instead")]]
Theme* themeSingleton();
```

### 5.5 CMake Visibility Control

[REQ-HDR-044] Every shared library target MUST set:

```cmake
set_target_properties(LingmoTheme PROPERTIES
    CXX_VISIBILITY_PRESET hidden
    VISIBILITY_INLINES_HIDDEN ON
)
```

> *Rationale*: Hidden-by-default visibility ensures that only explicitly exported symbols become part of the public ABI. This prevents internal symbols from leaking and causing ODR violations or symbol collisions.

## 6. ABI Boundaries

### 6.1 Public ABI

[REQ-HDR-045] The public ABI consists of every symbol annotated with the target's export macro. These symbols MUST remain stable within a major version.

[REQ-HDR-046] The following changes are ABI breaks and REQUIRE a MAJOR version increment:

| Change | Example |
|---|---|
| Remove a public class | Class definition removed |
| Remove a public member function | `void foo()` removed |
| Change a function signature | `void foo(int)` → `void foo(double)` |
| Add a virtual function to a non-final class | `virtual void bar()` added |
| Reorder virtual functions | Virtual table layout changes |
| Change the size of a public type | New member variable added |
| Change the alignment of a public type | `alignas` specifier changed |
| Change the type of a public member | `int count` → `unsigned count` |
| Remove or rename a public enum value | `enum Color { Red }` → `enum Color { Blue }` |
| Change the inheritance hierarchy | Class now inherits from a different base |

### 6.2 Private ABI

[REQ-HDR-047] Private ABI consists of all symbols NOT annotated with the export macro. Private ABI MAY change at any time within a major version.

[REQ-HDR-048] Private symbols MUST be hidden from the dynamic symbol table. This is enforced by the visibility settings in Section 5.5.

### 6.3 Inline Functions

[REQ-HDR-049] Functions defined `inline` in a public header become part of the public ABI. Once inlined, their implementation MUST NOT change in a way that alters behavior within a major version.

[REQ-HDR-050] Inline functions in public headers SHOULD be limited to:

- Trivial accessors and mutators
- Non-virtual delegating calls to private implementation methods
- `constexpr` utility functions

[REQ-HDR-051] Inline functions MUST NOT contain complex logic that is likely to change. Any inline function exceeding 10 logical lines MUST be justified in a code comment.

### 6.4 Templates

[REQ-HDR-052] Explicit template instantiations that are exported become part of the public ABI. They MUST be explicitly instantiated in exactly one translation unit and declared `extern template` in the public header.

[REQ-HDR-053] Template specializations in public headers MUST be stable within a major version. Adding or removing a specialization is an ABI break.

[REQ-HDR-054] Template definitions that are fully defined in a public header (not explicitly instantiated) are instantiated by the consumer and are NOT part of the library's ABI. However, their source stability is still governed by semantic versioning at the source level.

### 6.5 constexpr and consteval

[REQ-HDR-055] `constexpr` and `consteval` functions defined in public headers are subject to the same ABI rules as inline functions (Section 6.3). Their values at compile time are not ABI, but their runtime invocation path is.

[REQ-HDR-056] A function that is `constexpr` in version N MUST remain `constexpr` in version N+1 within the same major version. Removing `constexpr` is an ABI break if the function is used in compile-time contexts by consumers.

### 6.6 Header-Only Utilities

[REQ-HDR-057] Header-only utilities (utilities defined entirely in headers with no corresponding `.cpp` file) MUST be placed in a `detail/` subdirectory of `include/`:

```
include/LingmoTheme/detail/StringHelpers.h
```

[REQ-HDR-058] Header-only utilities MUST be contained in an `inline namespace`:

```cpp
namespace Lingmo {
inline namespace v1 {
namespace detail {
    // header-only utility declarations
} // namespace detail
} // inline namespace v1
} // namespace Lingmo
```

[REQ-HDR-059] Header-only utilities MUST NOT depend on any private symbols from the library. They MAY depend only on other public headers and standard library facilities.

## 7. PIMPL

### 7.1 When PIMPL Is REQUIRED

[REQ-HDR-060] The PIMPL (Pointer to Implementation) idiom is REQUIRED for any public class that meets ALL of the following criteria:

1. The class is exported (annotated with the export macro)
2. The class is intended for direct consumer instantiation or inheritance
3. The class contains member variables that are not trivial (std::string, QDateTime, containers, etc.) or that depend on private types

[REQ-HDR-061] The following class types are EXEMPT from the PIMPL requirement:

- Value types that serve as simple data containers (all members public, no invariants)
- Error types and exception types
- Thin wrapper classes that delegate entirely to a PIMPL-enabled class
- Abstract base classes (interfaces) with no member variables

### 7.2 PIMPL Convention

[REQ-HDR-062] The private implementation class MUST be named `ClassName::Private` and declared in the corresponding `_p.h` private header.

[REQ-HDR-063] The public class MUST own the private implementation through a `QExplicitlySharedDataPointer`, `std::unique_ptr`, or a `QPointer`. Raw `new`/`delete` ownership is FORBIDDEN.

[REQ-HDR-064] The destructor of the public class MUST be defined in the `.cpp` file (not `= default` in the header) to ensure the private implementation type is complete at the point of destruction:

```cpp
// Theme.h
class LINGMOTHEME_EXPORT Theme {
public:
    ~Theme();
private:
    std::unique_ptr<Private> d;
};

// Theme.cpp
Theme::~Theme() = default;
```

### 7.3 Forward Declarations

[REQ-HDR-065] The public header MUST forward-declare the Private class. The full definition MUST appear only in the private header:

```cpp
// Theme.h — public header
class LINGMOTHEME_EXPORT Theme {
public:
    Theme();
    ~Theme();
    int value() const;
private:
    class Private;
    std::unique_ptr<Private> d;
};

// Theme_p.h — private header
class Theme::Private {
public:
    int value = 0;
};
```

### 7.4 Binary Compatibility Guarantee

[REQ-HDR-066] PIMPL guarantees that changes to the private implementation (adding, removing, or reordering member variables; changing internal logic) do NOT break binary compatibility. Such changes MAY be made within a minor version.

[REQ-HDR-067] Adding or removing virtual functions from the public class, even with PIMPL, is an ABI break (Section 6.1).

## 8. Generated Headers

### 8.1 Classification

[REQ-HDR-068] Generated headers are files produced by build-system tools rather than written by developers. They fall into two categories:

| Category | Tools | Example Output |
|---|---|---|
| Build-system generated | CMake's `configure_file()`, `generate_export_header` | `LingmoThemeExport.h`, `LingmoThemeVersion.h` |
| Qt meta-object | `moc`, `qmltyperegistrar` | `moc_Theme.cpp`, `LingmoThemePlugin.qmltypes` |

### 8.2 Build-System Generated Headers

[REQ-HDR-069] Build-system generated headers that are part of the public API (export headers, version headers) MUST be generated into the `include/<TargetName>/` directory in the build tree. They MUST be installed alongside hand-written public headers.

[REQ-HDR-070] Build-system generated headers that are internal (configuration headers with platform-specific defines) MUST be generated into a `generated/` subdirectory beneath `src/` in the build tree:

```cmake
target_include_directories(LingmoTheme PRIVATE
    "$<BUILD_INTERFACE:${CMAKE_CURRENT_BINARY_DIR}/src/generated>"
)
```

### 8.3 Qt Meta-Object Generated Files

[REQ-HDR-071] Qt meta-object generated files (MOC output) for public classes MUST NOT be committed to the repository. They MUST be generated at build time and placed in the build directory.

[REQ-HDR-072] For public headers that contain Q_OBJECT macros, the corresponding `.cpp` file MUST include the generated MOC file at its end:

```cpp
// Theme.cpp
#include "Theme.h"
// ... implementation ...
#include "moc_Theme.cpp"
```

[REQ-HDR-073] Alternatively, CMake MAY be configured to automatically handle MOC via:

```cmake
set_target_properties(LingmoTheme PROPERTIES
    AUTOMOC ON
    AUTOMOC_MOC_NAMESPACE Lingmo
)
```

### 8.4 QML Type Registration

[REQ-HDR-074] QML type registration generated files (`qmltypes`, type registration source) MUST be generated into the build tree. They MUST NOT be committed.

[REQ-HDR-075] The generated QML type registration file MUST be installed alongside the QML module it serves, per SPEC-REPO-001 §5.5.

## 9. Third-Party Headers

### 9.1 Vendored Libraries

[REQ-HDR-076] A vendored library is a third-party dependency whose source is copied into the Lingmo repository tree. Vendoring is DISCOURAGED and MUST be approved by the architecture team.

[REQ-HDR-077] Vendored library headers MUST be placed in a `3rdparty/` directory at the repository root:

```
3rdparty/
└── tinyxml2/
    ├── tinyxml2.h
    └── tinyxml2.cpp
```

[REQ-HDR-078] Vendored headers MUST NOT be installed. They MUST be treated as private to the repository.

[REQ-HDR-079] Vendored headers MUST be included using quoted includes with a path relative to the `3rdparty/` root:

```cpp
#include "tinyxml2/tinyxml2.h"
```

### 9.2 Wrapper Headers

[REQ-HDR-080] If a third-party library requires platform-specific adaptation or a simplified interface, a wrapper header MAY be created. Wrapper headers MUST reside in the `detail/` subdirectory of the public include directory:

```
include/LingmoTheme/detail/DBusWrapper.h
```

[REQ-HDR-081] Wrapper headers MUST NOT expose third-party types in the public API unless those types are themselves part of the public API specification (e.g., Qt types).

### 9.3 Include Order with Third-Party

[REQ-HDR-082] Third-party library includes MUST follow the ordering defined in Section 10.3. They MUST be clearly separated from Lingmo and Qt includes by blank lines and section comments.

### 9.4 External Dependency Headers

[REQ-HDR-083] External dependencies (libraries installed on the system, found via `find_package`) MUST be included using angle-bracket syntax with the canonical path:

```cpp
#include <KScreen/Config.h>
#include <systemd/sd-journal.h>
```

[REQ-HDR-084] External dependency includes MUST NOT be placed in public headers unless the dependency type is part of the public API. If unavoidable, the dependency MUST be listed in the CMake `PUBLIC` link requirements.

## 10. Include Order

### 10.1 Mandatory Order

[REQ-HDR-085] Every `.cpp` file MUST order its includes as follows, with each group separated by a blank line:

```
// Group 1: Corresponding header (the .h for this .cpp)
// Group 2: Lingmo public headers (same target first, then other targets)
// Group 3: Lingmo private headers (only for .cpp files)
// Group 4: Qt headers
// Group 5: Standard Library headers
// Group 6: Third-party library headers
```

[REQ-HDR-086] Within each group, includes MUST be sorted lexicographically.

### 10.2 Header File Include Order

[REQ-HDR-087] Public header files (`.h`) MUST use the following include order:

```
// Group 1: #pragma once (first line)
// Group 2: Export header
// Group 3: Qt headers
// Group 4: Lingmo public headers
// Group 5: Standard Library headers
// Group 6: Forward declarations
```

### 10.3 Complete Example

```cpp
// src/LingmoTheme/Theme.cpp

// Group 1: Corresponding header
#include "Theme.h"

// Group 2: Lingmo public headers (same target first)
#include <LingmoTheme/ThemeExport.h>
#include <LingmoTheme/ThemeSettings.h>
#include <LingmoConfig/Config.h>

// Group 3: Lingmo private headers
#include "private/Theme_p.h"

// Group 4: Qt headers
#include <QDateTime>
#include <QDebug>
#include <QString>

// Group 5: Standard Library headers
#include <algorithm>
#include <memory>
#include <vector>

// Group 6: Third-party library headers
#include <systemd/sd-journal.h>
```

### 10.4 Exceptions

[REQ-HDR-088] The mandatory include order MAY be violated ONLY when a specific include order is required by the semantics of the included headers (e.g., a configuration header that must precede all other includes). Such violations MUST be documented in a comment.

[REQ-HDR-089] Platform-specific `#ifdef` blocks that require different include orders MUST isolate each variant in its own `#ifdef`/`#endif` block, each conforming to the mandatory order internally.

## 11. Installation

### 11.1 Which Headers Are Installed

[REQ-HDR-090] Only headers from the `include/<TargetName>/` directory SHALL be installed. All other headers (private, internal, vendored, generated internal) MUST NOT be installed.

[REQ-HDR-091] The following header types are installed:

| Header Type | Installed? | Destination |
|---|---|---|
| Public API headers | YES | `${CMAKE_INSTALL_INCLUDEDIR}/<TargetName>/` |
| Export header | YES | `${CMAKE_INSTALL_INCLUDEDIR}/<TargetName>/` |
| Version header | YES | `${CMAKE_INSTALL_INCLUDEDIR}/<TargetName>/` |
| Module root header | YES | `${CMAKE_INSTALL_INCLUDEDIR}/<TargetName>/` |
| Private headers (`_p.h`) | NO | — |
| Internal headers (`detail/`) | NO | — |
| Vendored headers | NO | — |
| Generated internal headers | NO | — |

### 11.2 Install Destination

[REQ-HDR-092] Public headers MUST install to:

```
${CMAKE_INSTALL_INCLUDEDIR}/<TargetName>/
```

Where `${CMAKE_INSTALL_INCLUDEDIR}` defaults to `<prefix>/include`.

### 11.3 Versioned Include Directories

[REQ-HDR-093] The installed include path MUST NOT include a version component:

```
<prefix>/include/LingmoTheme/Theme.h       # CORRECT
<prefix>/include/LingmoTheme-1.0/Theme.h  # FORBIDDEN
```

> *Rationale*: Versioned include directories cause unnecessary friction during upgrades. Version compatibility is enforced at the binary level through soname, not through include paths.

### 11.4 CMake Install Rules

[REQ-HDR-094] The CMake install rule for public headers MUST use the following pattern:

```cmake
install(
    DIRECTORY include/
    DESTINATION ${CMAKE_INSTALL_INCLUDEDIR}
    FILES_MATCHING
        PATTERN "*.h"
    COMPONENT devel
)
```

[REQ-HDR-095] If a `detail/` subdirectory exists inside `include/`, it MUST be excluded from installation unless its contents are explicitly part of the public API:

```cmake
install(
    DIRECTORY include/
    DESTINATION ${CMAKE_INSTALL_INCLUDEDIR}
    FILES_MATCHING
        PATTERN "*.h"
    PATTERN "detail" EXCLUDE
    COMPONENT devel
)
```

### 11.5 Header-Only Libraries

[REQ-HDR-096] Header-only libraries MUST still follow the `include/<TargetName>/` layout. Their CMake install rule MUST install all headers and provide an appropriate CMake config file for `find_package`.

[REQ-HDR-097] Header-only libraries MUST set:

```cmake
add_library(LingmoUtils INTERFACE)
target_include_directories(LingmoUtils
    INTERFACE
        "$<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>"
        "$<INSTALL_INTERFACE:${CMAKE_INSTALL_INCLUDEDIR}>"
)
```

## 12. Compliance Checklist

| ID | Requirement | Verification Method | Pass/Fail |
|---|---|---|---|
| REQ-HDR-001 | Public headers in `include/` | Directory listing check |
| REQ-HDR-002 | No public headers in `src/` | Automated scan of `src/` for `.h` files with export macros |
| REQ-HDR-003 | Mirror CMake target name in `include/` | CMake target vs directory name comparison |
| REQ-HDR-004 | Target name matches REPO-001 §6.3 | Naming convention check |
| REQ-HDR-005 | Multi-target repos have per-target subdirs | Repository audit |
| REQ-HDR-006 | Module root header exists | File existence check |
| REQ-HDR-007 | Root header has only includes | Content scan |
| REQ-HDR-008 | Root header structure | Content scan |

## Appendix B: Migration from SPEC-REPO-001

Repositories that previously followed SPEC-REPO-001 Sections 4 and 5.1–5.2 MUST migrate to this specification as follows:

| Old Rule (REPO-001) | New Rule (REPO-002) | Migration Action |
|---|---|---|
| Public headers in `include/` OR `src/` | Public headers MUST be in `include/` | Move public headers from `src/` to `include/<TargetName>/` |
| No subdirectory required under `include/` | Subdirectory must match CMake target name | Create `include/<TargetName>/` and update includes |
| Export header named `<Module>Export.h` in same dir | Same rule, now REQUIRED auto-generated | Add `generate_export_header` to CMake |
| Private headers in `src/` with `_p.h` suffix | Private headers in `src/<TargetName>/private/` with `_p.h` suffix | Move private headers to `private/` subdirectory |
| Internal headers in `src/detail/` | Internal headers in `src/<TargetName>/detail/` | Move internal headers to scoped `detail/` directory |
